# 문제지 PDF 저장 화면을 기존 출력 템플릿 기반으로 되돌리는 계획

> **에이전트 작업 지침:** 이 계획은 체크박스(`- [ ]`) 단위로 실행합니다. 각 단계는 **분석 → 계획 → 검증** loop를 따르며, 검증을 통과하기 전에는 다음 단계로 진행하지 않습니다.

## 목표
현재 `PDF 저장 설정` 화면은
- 좌측: 설정 패널
- 우측: pdfmake 기반 브라우저 PDF viewer

구조로 되어 있다.

하지만 사용자가 원하는 최종 방향은 다음과 같다.

1. **오른쪽 미리보기와 최종 저장/출력이 같은 템플릿**을 사용해야 한다.
2. 그 템플릿은 **PDF 저장 수정 요청 이전의 기존 출력 템플릿(`exportToPDF()` HTML print 템플릿)** 이어야 한다.
3. 좌측 설정 패널에서 바꾸는 아래 값이 **즉시 우측 미리보기에 반영**되어야 한다.
   - 표시모드
   - 레이아웃
   - 문제 순서
4. 최종 `PDF 저장` / `출력`도 **같은 미리보기 결과와 동일**해야 한다.

즉, 이번 작업의 본질은:

> **viewer만 바꾸는 것이 아니라, “미리보기 엔진”과 “최종 출력 엔진”을 다시 하나로 통일하는 것**

이다.

---

## 현재 구조 분석

### 현재 저장 흐름
현재 코드 기준으로는 출력 엔진이 두 개다.

#### 1) 기존 엔진
- 파일: `src/lib/export-utils.ts`
- 함수: `exportToPDF(examPaper)`
- 방식:
  - print-friendly HTML 생성
  - 새 창 열기
  - CSS 기반 1단/2단 레이아웃
  - `window.print()` 호출

#### 2) 현재 워크스페이스 엔진
- 파일: `src/lib/exam-paper-pdf.ts`
- 방식:
  - pdfmake로 PDF blob 생성
  - 오른쪽 iframe/browser PDF viewer에서 표시

### 현재 문제
지금은 사용자가 좌측에서 설정을 바꿔도,
- 오른쪽 미리보기는 pdfmake 결과
- 실제 저장/출력 템플릿은 원래 HTML 템플릿과 다를 수 있음

즉,
> **미리보기와 최종 저장 결과가 서로 다를 가능성**
이 구조적으로 존재한다.

이게 사용자 요구와 충돌한다.

---

## 요구사항 재정의

이번 계획에서 만족해야 하는 동작은 다음과 같다.

### 요구사항 A — 단일 출력 엔진
오른쪽 미리보기와 최종 출력은 **동일한 HTML 템플릿**을 사용한다.

### 요구사항 B — 즉시 반영
좌측 설정 변경 시 아래가 **즉시 우측 미리보기**에 반영된다.
- 표시모드
- 레이아웃
- 문제 순서

### 요구사항 C — 기존 템플릿 회귀
최종 저장/출력물은 **PDF 저장 수정 요청 이전 템플릿과 최대한 동일한 구조/스타일**을 유지해야 한다.

### 요구사항 D — 동작 일치
우측 미리보기에서 보이는 결과와
- `출력`
- `PDF 저장`
결과가 같아야 한다.

---

## 권장 해결 방향

## 방향 1 — 기존 HTML print 템플릿을 “미리보기 가능 엔진”으로 승격 (권장)
핵심 아이디어:
- `src/lib/export-utils.ts`의 기존 HTML 출력 템플릿을 재사용한다.
- 다만 더 이상 바로 `window.print()`만 하지 않고,
- **같은 HTML을 iframe/srcDoc 기반으로 오른쪽에 미리보기**한다.
- 최종 출력/저장은 그 미리보기와 **동일한 HTML**을 사용한다.

### 구체 방식
1. 기존 `exportToPDF()` 내부의 HTML 생성 로직을 분리한다.
   - 예: `buildExamPaperPrintHtml(examPaper)`
2. 워크스페이스 오른쪽 iframe은
   - 이 HTML 문자열을 `srcDoc` 또는 blob URL로 렌더한다.
3. `PDF 저장`/`출력` 버튼은
   - 같은 HTML을 새 창에 띄워 print를 호출하거나,
   - 같은 HTML을 인쇄 전용 창으로 넘긴다.

### 장점
- 기존 출력 템플릿을 거의 그대로 살릴 수 있다.
- 미리보기와 최종 결과가 일치한다.
- 표시모드/레이아웃/문제순서 draft 상태를 그대로 템플릿에 반영할 수 있다.

### 단점
- 브라우저 내장 PDF viewer 느낌은 줄어들고,
  실제로는 “HTML print preview에 가까운 iframe”이 된다.
- 하지만 사용자 요구는 이미 “기존 출력 템플릿으로 되돌리되, 미리보기도 같게”였으므로 이 방향이 가장 적합하다.

---

## 방향 2 — pdfmake 결과를 기존 템플릿처럼 재현 (비권장)
이 방향은 현재 `exam-paper-pdf.ts`를 계속 발전시켜서,
스타일과 레이아웃을 옛날 출력 템플릿처럼 최대한 맞추는 방법이다.

### 장점
- PDF viewer 형태를 유지하기 쉽다.

### 단점
- 지금까지 겪은 문제처럼
  - 2단 배치
  - 페이지 경계
  - 템플릿 차이
  - 문장 잘림
  문제를 계속 안고 가야 한다.
- 미리보기와 출력 일치는 쉽지만, 구현 난이도가 훨씬 높다.

### 결론
이번 요구에는 부적합하다.

---

# 최종 권장안

> **기존 HTML 출력 템플릿을 공통 엔진으로 되돌리고, 오른쪽 미리보기 역시 그 HTML 템플릿을 iframe으로 보여주는 방식**

즉, 새 구조는:

- 좌측: 현재 설정 패널 유지
- 우측: `buildExamPaperPrintHtml(draftExamPaper)` 결과를 iframe 미리보기
- 출력/저장: 같은 HTML 결과를 print/save에 사용

# 리스크와 대응

## 리스크 1 — iframe 안 print CSS와 실제 인쇄 창 CSS 차이
동일 HTML을 쓰더라도 렌더 컨텍스트가 달라질 수 있다.

**대응:**
- preview HTML과 print HTML을 같은 builder에서 생성
- CSS도 같은 템플릿에서 공유

## 리스크 2 — 기존 템플릿이 현재 draft 상태를 완전히 반영하지 못할 수 있음
특히 문제 순서/모드/레이아웃을 넘기는 path를 다시 점검해야 한다.

**대응:**
- draft exam paper object를 최종 source of truth로 사용

## 리스크 3 — 기존 pdfmake 관련 코드가 남아 혼란을 줄 수 있음

**대응:**
- 이번 단계에서는 pdfmake path를 완전 삭제하지 않더라도,
  워크스페이스에서는 더 이상 사용하지 않도록 명확히 분리

# 최종 성공 기준

아래가 모두 만족될 때 성공이다.
1. 오른쪽 미리보기가 기존 출력 템플릿 기반으로 보인다.
2. 표시모드/레이아웃/문제순서 변경이 즉시 미리보기에 반영된다.
3. `PDF 저장` / `출력` 결과가 우측 미리보기와 동일하다.
4. 기존 출력 템플릿의 스타일/구조가 최대한 보존된다.
5. 각 loop는 검증 통과 후에만 종료된다.
