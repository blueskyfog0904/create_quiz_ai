## 0. 이 문서 쓰는 법과 공통 규칙

### 0-1. 각 절차의 구성

절차마다 **언제 / 무엇을 본다 / 무엇을 한다 / 누가 / 고객 안내 문구** 순서로 적었습니다. 고객 안내 문구는 [12절](#12-고객-안내-문구-모음)에 모아 두었습니다.

### 0-2. 누가 실행하나

**지금은 모든 절차를 대표가 직접 실행합니다.** 고객 응대(CS) 담당자에게 따로 권한을 나눠 주는 기능은 아직 없습니다. 지금은 관리자 계정이면 누구나 관리자 화면의 모든 기능을 쓸 수 있습니다(코드 확인: 관리자 여부만 검사합니다).

### 0-3. SQL 규칙 — 반드시 지킬 것

| 종류 | 규칙 |
|---|---|
| **조회(SELECT)** | 자유롭게 실행해도 됩니다. 이 문서에서 **"조회"라고 적은 SELECT**는 모두 읽기 전용이며 Supabase SQL Editor에 그대로 붙여 넣으면 됩니다. **단, `stop_payment_sales`·`resume_payment_sales`가 들어간 문장은 SELECT로 시작해도 조회가 아니라 스위치를 바꾸는 실행입니다(아래 셋째 줄).** |
| **돈·개인정보를 바꾸는 SQL**(UPDATE, DELETE, INSERT) | **즉석에서 만들어 실행하지 않습니다.** 필요해지면 ① SQL 작성 → ② 운영 DB에서 `BEGIN … ROLLBACK`으로 리허설(실제로는 아무것도 바꾸지 않고 결과만 확인) → ③ 전문 검증 3명(지급·환불·마이그레이션 관점) 통과 → ④ 대표 승인 → ⑤ 적용 순서로 합니다. 보통 1~2일 걸립니다. |
| **미리 검증이 끝난 SQL** | **판매 중지·재개 함수뿐**입니다([2절](#2-rb-2-충전-판매-중지재개)). 이것만 바로 실행해도 됩니다. 이 두 문장은 **시험 삼아 실행하지 않습니다.** 실행하는 즉시 고객의 충전이 막히거나 열립니다. |

### 0-4. DB를 바꾸기 전에는 덤프(백업)부터

Supabase 무료 플랜이라 **자동 백업이 없습니다.** DB 내용을 바꾸는 작업(위 표의 둘째 줄)을 하기 전에는 반드시 덤프(DB 전체를 파일로 내려받은 것)를 먼저 떠 둡니다. 덤프 방법은 서울 이전 때 쓴 스크립트 `scripts/supabase-seoul-migration/h1-dump.sh`가 저장소에 있습니다. 이 스크립트를 평소 백업용으로 그대로 써도 되는지는 **확인 필요**입니다(이전 작업용으로 만든 것입니다). 판매 중지·재개 함수는 스위치 값 하나만 바꾸므로 덤프 없이 실행해도 됩니다.

### 0-5. 자주 나오는 말

| 말 | 뜻 |
|---|---|
| 충전 판매 스위치 | 고객이 새로 크레딧을 충전(결제)할 수 있는지 정하는 값입니다. **전체 스위치**와 **페이앱 스위치** 두 개가 있고, 둘 다 켜져 있어야 충전할 수 있습니다. 표 `payment_runtime_config`에 있습니다. |
| 결제 통보 | 고객이 결제·취소하면 페이앱이 우리 사이트로 보내는 알림입니다. 이 통보를 받아야 크레딧이 지급됩니다. |
| 결제요청번호 | 페이앱이 결제 한 건마다 붙이는 번호입니다(페이앱에서는 `mul_no`라고 부릅니다). 우리 DB에서는 `payment_provider_transactions.provider_transaction_id` 칸에 있습니다. 페이앱 관리자 화면에서 결제를 찾을 때 씁니다. |
| 자동 점검 | 5분마다 DB가 스스로 도는 검사입니다. 돈이 걸린 이상을 발견하면 페이앱 스위치를 끄고 경보를 남깁니다. |
| 대사 작업 | 5분마다 우리 서버가 미처리 결제·취소를 다시 처리하는 작업입니다. |
| 수동 확인 | 자동으로 처리하지 못해 사람이 페이앱 관리자 화면과 대조해 결정해야 하는 상태입니다(`manual_review`). |
| 원천 | 크레딧이 들어온 한 묶음(충전 1건, 관리자 지급 1건 등)을 말합니다. 표 `credit_sources`입니다. |

### 0-6. 자동으로 도는 작업 3개

Supabase 안에서 정해진 시간마다 실행됩니다. 작업은 항상 **이름**으로 찾습니다.

| 작업 이름 | 주기 | 하는 일 |
|---|---|---|
| `payment-reconciliation-http-5m` | 5분마다 | 우리 서버의 대사 작업을 부릅니다(미처리 결제·취소 재처리). |
| `payment-reconciliation-health-5m` | 5분마다 | 자동 점검 함수 `enforce_payment_reconciliation_health()`를 실행합니다. |
| `market-cleanup-daily` | 매일 한국 시간 새벽 4시 | 문제마켓 정리([11-3](#11-3-매일-새벽-4시-자동-정리)). |

최근 실행 결과를 보는 조회입니다.

```sql
SELECT j.jobname,
       d.status,
       d.return_message,
       d.start_time AT TIME ZONE 'Asia/Seoul' AS 시작_한국시간
  FROM cron.job_run_details d
  JOIN cron.job j ON j.jobid = d.jobid
 WHERE j.jobname IN ('payment-reconciliation-http-5m',
                     'payment-reconciliation-health-5m',
                     'market-cleanup-daily')
 ORDER BY d.start_time DESC
 LIMIT 30;
```

`status`가 `succeeded`면 정상입니다. 단, `payment-reconciliation-http-5m`과 `market-cleanup-daily`는 "서버를 불렀다"까지만 `succeeded`로 나옵니다. 서버가 실제로 일을 잘 끝냈는지는 [1-2](#1-2-경보-코드별-대응표)의 조회 ④(대사 작업 상태)와 [11-3](#11-3-매일-새벽-4시-자동-정리)의 조회로 봅니다.

## 1. RB-1 결제 경보·사이트 장애 대응

- **언제**: 관리자 화면에 경보가 보일 때, 판매가 꺼졌을 때, 사이트가 안 열릴 때, 고객이 결제 문제를 알려 왔을 때.
- **누가**: 대표.

### 1-1. 경보를 어디서 보나

| 화면 | 주소 | 보이는 것 |
|---|---|---|
| 관리자 대시보드 | `/admin` | 맨 위에 충전 판매 상태(초록 "충전 판매 중" 또는 빨간 "충전 판매 중지됨"). 그 아래 **"처리 대기"** 카드에 6가지 건수: 미해소 결제 경보, 수동 확인이 필요한 결제 주문, 충전 환불 — 재처리·수동 확인, 충전 환불 — 승인 대기, 문제마켓 환불 대기, 답변 대기 문의. 숫자가 "확인 불가"로 나오면 0건이 아니라 세지 못했다는 뜻입니다. |
| 환불 관리 | `/admin/refunds` | 맨 위에 충전 판매 상태. 그 아래 **"결제 확인 필요"** 카드 안에 "미해소 결제 경보" 목록과 "수동 확인 주문" 표. 그 아래 충전 환불 요청 표, 맨 아래 "문제마켓 환불" 표. |

> **주의 — 지금은 경보가 밖으로 알려지지 않습니다.** 슬랙·메일·문자로 경보를 보내는 기능은 아직 없습니다(코드 확인). 일부 경보는 관리자 계정에 사이트 알림("페이앱 결제 확인 필요")을 남기지만, 그 알림은 옛 화면 헤더의 종 모양에서만 보이고 관리자 화면(`/admin`)에는 표시되지 않습니다. **그러므로 출시 뒤에는 `/admin`을 하루에도 여러 번 직접 열어 "처리 대기"를 확인해야 합니다.**

SQL로 미해소 경보를 보는 조회입니다.

```sql
SELECT code,
       severity,
       message,
       details,
       created_at AT TIME ZONE 'Asia/Seoul' AS 발생_한국시간
  FROM public.payment_reconciliation_alerts
 WHERE resolved_at IS NULL
 ORDER BY created_at;
```

`severity`가 `critical`이면 화면에 "긴급", `warning`이면 "주의"로 표시됩니다.

### 1-2. 경보 코드별 대응표

**경보를 해소하는 방법(공통)**: `/admin/refunds` → "미해소 결제 경보"에서 해당 경보의 **"해소"** 버튼 → "처리 메모 (필수)"에 확인한 원인과 처리 내용을 적고 **"해소 기록"**. 다음 세 가지를 꼭 기억합니다.

1. **해소해도 판매 스위치는 바뀌지 않습니다.** 재개는 [2-4](#2-4-재개하기-sql)에서 따로 합니다.
2. **원인이 남아 있으면 자동 점검이 5분 안에 같은 경보를 다시 만듭니다.** 먼저 원인을 처리하고 해소합니다.
3. **같은 코드의 미해소 경보가 남아 있으면 같은 문제가 또 생겨도 새 경보가 안 생길 수 있습니다.** 처리한 경보는 그날 해소합니다.

"수동 확인 주문" 표에서 **"확인 처리"**를 하면 그 주문에 연결된 경보는 함께 해소됩니다. 표에 "아래 환불 요청에서 처리"라고 나오는 주문은 충전 환불 요청 표에서 "수동 완료"를 한 뒤 경보를 직접 해소합니다.

#### (가) 자동 점검이 만드는 경보 — 판매가 꺼질 수 있는 것

| 코드 | 뜻 | 판매 자동 중지 | 조치 |
|---|---|---|---|
| `PAYAPP_PAID_UNFULFILLED` | 결제완료 통보는 받았는데 10분 넘게 크레딧이 지급되지 않은 건이 있습니다. | **예**(페이앱 스위치) | 아래 조회 ①로 건을 찾습니다. 보통 주문이 "수동 확인 주문" 표에 올라옵니다. 페이앱 관리자 화면에서 결제가 실제로 됐는지 대조한 뒤 "확인 처리" → "결제 확인됨 (크레딧 지급)" → "처리 메모 (필수)"를 적고 "처리 기록"(창 사용법은 [1-5](#1-5-결제했는데-크레딧이-안-들어왔다는-문의)). 표에 없고 10~20분 뒤에도 그대로면 개발 담당자에게 알립니다. |
| `PAYAPP_CANCEL_UNPROCESSED` | 페이앱에서 취소(환불)됐는데 10분 넘게 우리 쪽 처리가 끝나지 않았고, 그 크레딧을 고객이 아직 쓸 수 있습니다. | **예** | 조회 ②로 건을 찾습니다. 대사 작업이 다시 처리하므로 10분쯤 기다려 봅니다. 그대로면 충전 환불 요청 표에 "수동 확인 필요"로 올라온 건을 "수동 완료"로 처리합니다. 환불 요청 표에도 없으면 개발 담당자에게 알립니다. |
| `PAYAPP_MONEY_RISK_REVIEW` | 돈이 걸린 수동 확인 주문이 있습니다. | **예** | 조회 ③으로 주문과 사유 코드를 봅니다. "수동 확인 주문" 표에서 처리합니다. 사유 코드의 뜻은 (라) 끝에 있는 '사유 코드' 표를 봅니다. |
| `PAYMENT_RECONCILIATION_REPEATED_FAILURE` | 대사 작업이 3회 연속 실패했습니다. | **예**(이때 스위치 기록에는 `PAYAPP_RECONCILIATION_UNHEALTHY`라고 남습니다) | 조회 ④로 마지막 오류를 봅니다. 사이트가 죽었을 가능성이 큽니다 → [1-3](#1-3-사이트나-결제-통보-주소가-죽었을-때). |
| `PAYMENT_RECONCILIATION_SCHEDULER_STALE` | 대사 작업의 성공 기록이 15분 넘게 갱신되지 않았습니다. | **예**(위와 같음) | 위와 같습니다. |

#### (나) 자동 점검이 만드는 경보 — 판매는 꺼지지 않는 것

| 코드 | 뜻 | 조치 |
|---|---|---|
| `PAYAPP_CANCEL_UNPROCESSED_FROZEN` | 페이앱 취소 처리가 10분 넘게 끝나지 않았지만, 그 크레딧은 묶여 있거나 아직 지급 전이라 고객이 쓸 수 없습니다. | 급하지 않습니다. 조회 ②로 확인하고, 충전 환불 요청 표에 올라온 건을 처리합니다. |

#### (다) 결제 통보를 받을 때 만들어지는 경보

통보 처리 코드(`src/lib/payapp-webhook-server.ts`)와 대사 작업, DB 함수가 만듭니다. **이 경보들만으로는 판매가 꺼지지 않습니다.** 다만 같은 주문이 수동 확인으로 넘어가면 (가)의 `PAYAPP_MONEY_RISK_REVIEW`가 따라올 수 있습니다.

| `PAYAPP_DOUBLE_REFUND_SUSPECTED` | 긴급 | 계좌 송금으로 환불한 결제가 페이앱에서도 취소됐거나, 이미 다른 방식으로 환불이 끝난 요청에 "계좌 송금 완료"가 입력됐습니다. **이중 환불 의심.** | 실제로 두 번 나갔는지(계좌 이체 내역 + 페이앱 취소 내역) 확인합니다. 두 번 나갔으면 고객에게 연락해 한쪽을 돌려받습니다. |

| `PAYAPP_PARTIAL_CANCEL_DEFERRED` | 주의 | 환불 처리 중인 결제에 부분취소가 통보됐습니다. 환불이 끝난 뒤 대사 작업이 정리합니다. | 기다렸다가 환불 요청이 끝났는지 확인합니다. |

| `PAYAPP_REFUND_PROCESSING_STUCK` | 주의 | 10분 넘게 끝나지 않은 환불을 "재처리 필요"로 돌렸습니다. | 페이앱 관리자 화면에서 그 결제가 취소됐는지 먼저 확인합니다([5-2](#5-2-상태의-뜻과-할-일)의 "재처리 필요"). |

위 표에 없는 코드가 "페이앱 통보 검증에 실패했습니다: …"라는 메시지와 함께 나오면, 통보 내용이 주문과 맞지 않아 무시된 경우입니다. 메시지의 사유를 적어 개발 담당자에게 알립니다.

> 참고: 페이앱은 **전액 취소만** 우리 사이트에서 요청합니다. 부분취소는 페이앱 관리자 화면에서 사람이 직접 했을 때만 생깁니다. 부분취소를 하지 않으면 위 "부분취소" 경보는 나오지 않습니다.

#### (라) 크레딧·마켓 환불에서 만들어지는 경보 (판매는 꺼지지 않음)

| 코드 | 뜻 | 조치 |
|---|---|---|
| `CREDIT_REFUND_FAILED` | 크레딧을 되돌려 주는 처리가 실패했습니다. | `details`의 `user_id`로 회원을 찾아 잔액을 확인하고, 못 돌려준 만큼 크레딧 지급(사유 카테고리 "환불")으로 보상합니다([6절](#6-rb-7-하자-상품-환불)). |

수동 확인 주문 표의 "사유" 칸에 나오는 코드(판매를 끄는 6가지)의 뜻입니다.

| 사유 코드 | 뜻 |
|---|---|
| `PAYAPP_FEEDBACK_MISMATCH` | 통보 내용(금액 등)이 주문과 다릅니다. |
| `PAYAPP_MUL_NO_CONFLICT` | 같은 결제요청번호가 다른 주문에 이미 쓰였습니다. |

| `PAYAPP_READY_CANCEL_FAILED` | 결제 준비 단계의 취소가 실패했습니다. |
| `PAYAPP_FULFILLMENT_RETRY_EXHAUSTED` | 크레딧 지급을 여러 번 시도했지만 실패했습니다. |
| `PAYAPP_CANCEL_HANDLING_FAILED` | 취소 처리에 실패했습니다. |

위 여섯 가지 뜻은 코드 이름과 주변 코드로 확인한 것입니다. 각 건의 정확한 사정은 표의 사유 설명(`failure_message`)을 함께 읽습니다.

#### (마) 카카오페이 관련 코드 — 지금은 나오지 않아야 함

`PAYMENT_RECONCILIATION_STALE_PAYMENT`, `PAYMENT_RECONCILIATION_MANUAL_REVIEW`, `KAKAOPAY_PARTIAL_CANCEL_UNPROCESSED`, `KAKAOPAY_PARTIAL_CANCEL_UNPROCESSED_FROZEN`은 카카오페이 주문에 대한 경보입니다. 카카오페이를 쓰지 않으므로 나올 일이 없습니다. 나온다면 개발 담당자에게 알립니다. 이 경보들은 카카오페이 스위치만 끄고 페이앱 판매에는 영향을 주지 않습니다.

#### 확인용 조회

① 결제완료인데 지급 안 된 건 (`PAYAPP_PAID_UNFULFILLED`)

```sql
SELECT po.order_id                    AS 주문번호,
       p.email                        AS 회원,
       po.plan_name_snapshot          AS 요금제,
       po.expected_amount             AS 금액,
       po.status                      AS 주문상태,
       po.failure_code                AS 사유코드,
       ppt.provider_transaction_id    AS 페이앱_결제요청번호,
       ppt.paid_feedback_recorded_at AT TIME ZONE 'Asia/Seoul' AS 결제통보_한국시간
  FROM public.payment_orders po
  JOIN public.payment_provider_transactions ppt ON ppt.payment_order_id = po.id
  LEFT JOIN public.profiles p ON p.id = po.user_id
 WHERE po.provider = 'payapp'
   AND ppt.paid_feedback_recorded_at IS NOT NULL
   AND po.source_id IS NULL
   AND ppt.cancel_feedback_recorded_at IS NULL
   AND ppt.partial_cancel_feedback_recorded_at IS NULL
 ORDER BY ppt.paid_feedback_recorded_at;
```

② 취소 통보를 받았는데 처리가 안 끝난 건 (`PAYAPP_CANCEL_UNPROCESSED`, `…_FROZEN`)

```sql
SELECT po.order_id                    AS 주문번호,
       p.email                        AS 회원,
       po.expected_amount             AS 금액,
       ppt.provider_transaction_id    AS 페이앱_결제요청번호,
       ppt.cancel_feedback_recorded_at AT TIME ZONE 'Asia/Seoul'         AS 취소통보_한국시간,
       ppt.partial_cancel_feedback_recorded_at AT TIME ZONE 'Asia/Seoul' AS 부분취소통보_한국시간,
       cs.status                      AS 크레딧상태,
       cs.remaining_credits           AS 남은크레딧
  FROM public.payment_orders po
  JOIN public.payment_provider_transactions ppt ON ppt.payment_order_id = po.id
  LEFT JOIN public.credit_sources cs ON cs.payment_order_id = po.id
  LEFT JOIN public.profiles p ON p.id = po.user_id
 WHERE po.provider = 'payapp'
   AND ((ppt.cancel_feedback_recorded_at IS NOT NULL AND ppt.cancel_processed_at IS NULL)
     OR (ppt.partial_cancel_feedback_recorded_at IS NOT NULL AND ppt.partial_cancel_processed_at IS NULL))
 ORDER BY po.created_at;
```

`크레딧상태`가 `active`면 고객이 그 크레딧을 쓸 수 있는 상태(판매가 꺼지는 경우)이고, `pending_refund`·`refunded`거나 비어 있으면 쓸 수 없는 상태입니다.

③ 수동 확인 주문 (`PAYAPP_MONEY_RISK_REVIEW`)

```sql
SELECT po.order_id                    AS 주문번호,
       p.email                        AS 회원,
       po.plan_name_snapshot          AS 요금제,
       po.expected_amount             AS 금액,
       po.failure_code                AS 사유코드,
       po.failure_message             AS 사유설명,
       ppt.provider_transaction_id    AS 페이앱_결제요청번호,
       po.created_at AT TIME ZONE 'Asia/Seoul' AS 주문_한국시간
  FROM public.payment_orders po
  LEFT JOIN public.payment_provider_transactions ppt ON ppt.payment_order_id = po.id
  LEFT JOIN public.profiles p ON p.id = po.user_id
 WHERE po.status = 'manual_review'
 ORDER BY po.created_at;
```

④ 대사 작업 상태 (`PAYMENT_RECONCILIATION_…`)

```sql
SELECT last_started_at   AT TIME ZONE 'Asia/Seoul' AS 마지막_시작,
       last_succeeded_at AT TIME ZONE 'Asia/Seoul' AS 마지막_성공,
       consecutive_failures                        AS 연속_실패,
       last_error_code,
       last_error_message
  FROM public.payment_reconciliation_scheduler
 WHERE id = 1;
```

정상이면 "마지막_성공"이 지금으로부터 5~10분 이내이고 "연속_실패"가 0입니다.

⑤ 처리되지 않은 페이앱 통보 (`PAYAPP_FEEDBACK_UNPROCESSED`)

```sql
SELECT transmission_id,
       event_type,
       processing_status,
       last_error_code,
       received_at AT TIME ZONE 'Asia/Seoul' AS 받은_한국시간
  FROM public.payment_webhook_events
 WHERE transmission_id LIKE 'payapp:%'
   AND (processing_status = 'pending'
     OR (processing_status = 'failed'
         AND COALESCE(last_error_code, '') NOT LIKE 'PROCESS:%')
     OR (processing_status = 'ignored'
         AND event_type IN ('PAYAPP_PAY_STATE_9', 'PAYAPP_PAY_STATE_64',
                            'PAYAPP_PAY_STATE_70', 'PAYAPP_PAY_STATE_71')
         AND COALESCE(last_error_code, '') <> 'PAYAPP_FOREIGN_FEEDBACK'))
 ORDER BY received_at DESC
 LIMIT 50;
```

`transmission_id`는 `payapp:결제요청번호:상태값` 모양입니다. 가운데 숫자가 페이앱 관리자 화면에서 찾을 결제요청번호입니다. 상태값 4는 결제완료, 9·64는 취소, 70·71은 부분취소입니다. 경보는 이 가운데 받은 지 30분이 넘은 통보만 셉니다.

### 1-3. 사이트나 결제 통보 주소가 죽었을 때

- **언제**: 사이트가 열리지 않을 때, `PAYMENT_RECONCILIATION_REPEATED_FAILURE`·`PAYMENT_RECONCILIATION_SCHEDULER_STALE` 경보가 떴을 때.
- **무엇을 본다**: Vercel 프로젝트의 **Deployments**(가장 최근 배포가 정상 상태인지)와 **Logs**(오류가 쏟아지는지). Supabase 프로젝트 상태도 함께 봅니다.
- **무엇을 한다**:
  1. 사이트 주소를 직접 열어 봅니다. 관리자 화면(`/admin`)이 열리면 "충전 판매 중지" 버튼으로 먼저 판매를 멈춥니다. 이미 빨간 띠("충전 판매 중지됨")가 보이면 판매가 꺼져 있는 것이고 버튼도 보이지 않으니 이 단계는 건너뜁니다. 관리자 화면도 안 열리면 Supabase SQL Editor에서 중지합니다([2-2](#2-2-sql로-중지하기)).
  2. Vercel Deployments에서 최근 배포가 실패했거나 방금 배포한 뒤부터 문제가 생겼다면, 개발 담당자에게 알려 이전 배포로 되돌립니다.
  3. 사이트가 죽은 동안 들어온 결제는 페이앱이 통보를 다시 보내 줍니다(재통보 횟수·간격은 페이앱 정책이라 **확인 필요**). 사이트가 살아난 뒤 [1-2](#1-2-경보-코드별-대응표)의 조회 ①·⑤와 페이앱 관리자 화면의 결제 내역을 대조해 빠진 건이 없는지 봅니다.
  4. 원인을 처리하고 경보를 해소한 뒤 [2-3](#2-3-재개-전-확인) → [2-4](#2-4-재개하기-sql) 순서로 재개합니다.
- **참고**: 페이앱이 통보를 보내는 우리 쪽 주소는 `/api/payments/webhooks/payapp`입니다. 이 주소는 페이앱 관리자 화면이 아니라 결제를 시작할 때마다 우리 서버가 지정합니다. 사이트가 죽었을 때 자동으로 알려 주는 외부 감시 서비스는 아직 연결되어 있지 않습니다.

### 1-4. 판매가 자동으로 꺼졌을 때의 순서

대시보드에 빨간 띠 **"충전 판매 중지됨 — 고객이 새로 충전할 수 없습니다 (페이앱 스위치 꺼짐)"**과 "마지막 변경: … · payment_reconciliation_health · (코드)"가 보이면 자동 점검이 끈 것입니다.

1. 빨간 띠의 코드(`PAYAPP_PAID_UNFULFILLED`, `PAYAPP_CANCEL_UNPROCESSED`, `PAYAPP_MONEY_RISK_REVIEW`, `PAYAPP_RECONCILIATION_UNHEALTHY` 중 하나)를 확인합니다. 조건이 여러 개여도 띠에는 첫 번째 하나만 적히므로, `/admin/refunds`의 미해소 경보를 모두 봅니다.
2. 이미 결제된 건의 지급·환불 처리는 판매가 꺼져 있어도 계속됩니다. 서두르지 말고 [1-2](#1-2-경보-코드별-대응표)의 표대로 원인을 하나씩 처리합니다.
3. 처리한 경보를 메모와 함께 해소합니다.
4. 필요하면 고객 공지를 올립니다([2-8](#2-8-판매-중지-동안-고객-안내)).
5. [2-3](#2-3-재개-전-확인)으로 막는 조건이 0건인지 확인하고 [2-4](#2-4-재개하기-sql)로 재개합니다.
6. 재개 10분 뒤 대시보드를 다시 열어 초록 "충전 판매 중"이 유지되는지 봅니다. 다시 꺼졌다면 원인이 남은 것입니다.

### 1-5. "결제했는데 크레딧이 안 들어왔다"는 문의

1. 회원 이메일로 최근 주문을 조회합니다(이메일만 바꿔 실행).

```sql
SELECT po.order_id                    AS 주문번호,
       po.plan_name_snapshot          AS 요금제,
       po.expected_amount             AS 금액,
       po.status                      AS 주문상태,
       po.failure_code                AS 사유코드,
       po.source_id IS NOT NULL       AS 크레딧_지급됨,
       ppt.provider_transaction_id    AS 페이앱_결제요청번호,
       ppt.paid_feedback_recorded_at AT TIME ZONE 'Asia/Seoul' AS 결제통보_한국시간,
       po.created_at AT TIME ZONE 'Asia/Seoul' AS 주문_한국시간
  FROM public.payment_orders po
  LEFT JOIN public.payment_provider_transactions ppt ON ppt.payment_order_id = po.id
  JOIN public.profiles p ON p.id = po.user_id
 WHERE p.email = '회원이메일@example.com'
 ORDER BY po.created_at DESC
 LIMIT 10;
```

2. 결과에 따라 처리합니다.

| 보이는 것 | 뜻 | 할 일 |
|---|---|---|
| `주문상태`가 `completed`, `크레딧_지급됨`이 true | 이미 지급됐습니다. | 마이페이지의 크레딧 내역(`/mypage/credits`)을 확인하시도록 안내합니다. |
| `주문상태`가 `manual_review` | 수동 확인이 필요합니다. | `/admin/refunds` → "수동 확인 주문"에서 페이앱 관리자 화면과 대조 후 "확인 처리". 실제 결제됐으면 "결제 확인됨 (크레딧 지급)", 결제가 안 됐으면 "미결제 확인 (만료 처리)". 결제완료 통보가 없었던 주문이면 "페이앱 결제요청번호" 칸을 반드시 채웁니다("결제 시각" 칸은 비우면 지금 시각으로 기록됩니다). 페이앱에서 이미 취소된 건이면 "취소 처리 확인"을 고르고 "외부 처리 방식"에서 실제로 한 방식을 선택합니다. 어느 것을 고르든 "처리 메모 (필수)"를 적고 **"처리 기록"**을 눌러야 끝납니다. |
| `주문상태`가 `preparing`·`ready`·`ready_unknown`이고 `결제통보_한국시간`이 비어 있음 | 결제창은 열렸지만 결제완료 통보를 아직 받지 못했습니다(주문은 30분 뒤 자동으로 만료됩니다). | 고객에게 결제가 실제로 승인됐는지 여쭙니다. 승인됐다고 하면 페이앱 관리자 화면에서 대조하고, 결제가 있으면 개발 담당자와 처리 방법을 정합니다(즉석 SQL 금지). |
| `주문상태`가 `fulfillment_pending`·`confirming` | 결제는 확인됐고 크레딧 지급을 다시 시도하는 중입니다. | 10분쯤 기다립니다. 실패가 이어지면 `manual_review`로 바뀌어 "수동 확인 주문" 표에 올라옵니다. |
| `주문상태`가 `refunded`·`cancel_pending` | 환불됐거나 취소 처리 중입니다. | `/admin/refunds`의 충전 환불 요청 표에서 그 건의 상태를 확인합니다. |
| `주문상태`가 `expired` 또는 `failed`이고 `결제통보_한국시간`이 비어 있음 | 우리 쪽에는 결제 기록이 없습니다. | 페이앱 관리자 화면에서 그 고객의 결제가 실제로 있는지 찾습니다. 결제가 있다면 **즉석 SQL로 고치지 말고** 개발 담당자와 처리 방법을 정합니다(0-3 규칙). |
| 주문이 아예 없음 | 다른 이메일로 가입했거나 결제창까지 가지 않았습니다. | 결제한 계정 이메일과 결제 시각·금액을 다시 여쭙니다. |

3. 고객 안내 문구는 [12-2](#12-2-결제됐는데-크레딧이-안-들어옴)를 씁니다.

### 1-6. 사이트 밖 결제(카페 판매) 통보 구분하기

페이앱 판매자 계정을 대표의 카페 판매에도 함께 쓰기 때문에, **사이트와 무관한 결제의 통보도 우리 사이트로 들어옵니다.** 이것은 예상된 일이고 실제 결제입니다. **페이앱 쪽 설정은 건드리지 않습니다.**

코드가 구분하는 방식은 이렇습니다.

| 통보의 모습 | 처리 | 경보 |
|---|---|---|
| 우리 주문번호가 들어 있지 않고, 결제요청번호로도 우리 주문을 찾지 못함 | 사이트 밖 결제로 보고 기록만 남깁니다(`payment_webhook_events`에 `ignored`, `PAYAPP_FOREIGN_FEEDBACK`). | **경보 없음** |
| 우리 주문번호가 들어 있는데 그 주문을 찾지 못함 | 이상한 통보로 봅니다. | `PAYAPP_FEEDBACK_ORDER_NOT_FOUND` |
| 부분취소 통보인데 원래 결제요청번호가 없음(사이트 밖 판매의 부분취소도 여기에 해당할 수 있음) | 찾을 단서가 없어 경보로 보냅니다. | `PAYAPP_FEEDBACK_ORDER_NOT_FOUND`(긴급) |

`PAYAPP_FEEDBACK_ORDER_NOT_FOUND`가 떴을 때 사이트 밖 결제인지 가리는 방법입니다.

1. 경보의 `details`에서 `mul_no`(결제요청번호), `order_id`(주문번호), `price`(금액), `pay_state`(상태 값)를 봅니다.
2. 페이앱 관리자 화면에서 그 결제요청번호의 결제를 찾아 **상품명·구매자·금액**을 봅니다. 카페 판매분이면 사이트와 무관합니다.
3. 우리 DB에 그 번호가 있는지 확인합니다(번호만 바꿔 실행). 결과가 0줄이면 사이트 주문이 아닙니다.

```sql
SELECT po.order_id, po.status, po.expected_amount, p.email
  FROM public.payment_provider_transactions ppt
  JOIN public.payment_orders po ON po.id = ppt.payment_order_id
  LEFT JOIN public.profiles p ON p.id = po.user_id
 WHERE ppt.provider = 'payapp'
   AND ppt.provider_transaction_id = '여기에_결제요청번호';
```

4. 사이트 밖 결제로 확인되면 "카페 판매분, 사이트 주문 아님"이라고 메모하고 해소합니다.
5. **사이트 결제인데 주문을 못 찾은 것 같으면**(금액이 요금제 가격과 같고 구매자가 사이트 회원) 해소하지 말고 개발 담당자에게 알립니다. 돈만 받고 크레딧을 못 준 상태일 수 있습니다.

사이트 밖 결제로 기록된 통보를 보는 조회입니다.

```sql
SELECT transmission_id,
       event_type,
       received_at AT TIME ZONE 'Asia/Seoul' AS 받은_한국시간
  FROM public.payment_webhook_events
 WHERE last_error_code = 'PAYAPP_FOREIGN_FEEDBACK'
 ORDER BY received_at DESC
 LIMIT 50;
```

`transmission_id`는 `payapp:결제요청번호:상태값` 모양입니다. 가운데 숫자로 페이앱 관리자 화면에서 그 결제를 찾을 수 있습니다.

## 2. RB-2 충전 판매 중지·재개

- **언제**: 결제에 이상이 있어 새 충전을 막아야 할 때(중지), 자동 또는 수동으로 꺼진 판매를 다시 열 때(재개).
- **누가**: 대표.
- **알아 둘 것**
  - 중지는 **새 충전 주문만** 막습니다. 이미 결제된 건의 크레딧 지급과 환불 처리는 계속됩니다. 크레딧으로 자료를 사는 것(문제마켓 구매)도 막지 않습니다.
  - 중지 전에 이미 결제창을 연 고객은 **최대 30분** 안에 결제를 마칠 수 있고, 그 건은 정상 지급됩니다. 그러니 중지 직후 30분 동안은 새 결제가 들어올 수 있습니다.
  - 스위치는 두 개입니다. **버튼은 전체 스위치**를 끄고, **자동 점검은 페이앱 스위치**를 끕니다. 둘 중 하나라도 꺼져 있으면 충전할 수 없습니다.
  - "누가·언제·왜" 기록 칸은 **하나뿐이라 마지막 변경 1건만 남습니다.** 버튼으로 끈 뒤 자동 점검이 또 끄면 자동 점검 기록으로 바뀝니다. 자동 점검의 사유는 결제 경보에도 남습니다.
  - 중지된 동안 고객의 충전 화면에는 "결제 기능을 준비 중입니다 / 현재 사용할 수 있는 결제수단이 없습니다. 잠시 후 다시 확인해 주세요."가 나옵니다.

### 2-0. 지금 상태 보기

```sql
SELECT master_accepts_new_orders  AS 전체_스위치,
       payapp_accepts_new_orders  AS 페이앱_스위치,
       changed_at AT TIME ZONE 'Asia/Seoul' AS 마지막_변경_한국시간,
       changed_by                 AS 바꾼_사람,
       change_ticket              AS 사유
  FROM public.payment_runtime_config
 WHERE id = true;
```

두 스위치가 모두 `true`여야 판매 중입니다. `바꾼_사람`이 `payment_reconciliation_health`면 자동 점검이, `admin:…`이면 관리자 버튼이 바꾼 것입니다. `사유`가 `MANUAL_STOP: …`이면 사람이 중지, `MANUAL_RESUME: …`이면 사람이 재개한 것입니다. `바꾼_사람`이 `migration_…`으로 시작하면 개발 작업으로 넣은 초기값입니다(2026-11-13 현재 값이 이것이고, 사유는 `PAYAPP_LAUNCH`입니다).

### 2-1. 버튼으로 중지하기 (가장 빠름)

1. `/admin`(관리자 대시보드) 또는 `/admin/refunds`(환불 관리) 맨 위의 **"충전 판매 중지"** 버튼을 누릅니다. (판매 중일 때만 보입니다.)
2. 창에서 **"중지 사유 (필수)"**에 무슨 일인지 적습니다(300자 이내).
3. **"판매 중지"**를 누릅니다. "충전 판매를 중지했습니다."가 나오고 맨 위가 빨간 띠로 바뀌면 끝입니다.
4. "충전 판매를 중지하지 못했습니다…"가 나오면 새로고침해 상태를 확인하고, 그대로 판매 중이면 [2-2](#2-2-sql로-중지하기)로 중지합니다.

이 버튼은 **중지만** 합니다. 화면에서는 다시 켤 수 없습니다.

### 2-2. SQL로 중지하기

관리자 화면이 열리지 않을 때 씁니다. Supabase SQL Editor에서 한 줄만 실행합니다. 이름과 사유는 실제 내용으로 바꿉니다.

```sql
SELECT public.stop_payment_sales('master', '처리자 이름', '중지 사유');
```

- `'master'`는 전체 스위치, `'payapp'`은 페이앱 스위치입니다. 보통 `'master'`를 씁니다(버튼과 같은 동작).
- 결과의 `master_accepts_new_orders`가 `false`면 중지된 것입니다. 이미 꺼져 있었다면 `changed`가 `false`로 나오고 기존 기록은 그대로 둡니다.

### 2-3. 재개 전 확인

1. **막는 조건이 남았는지** 봅니다.

```sql
SELECT public.payapp_sales_resume_blockers();
```

| 항목 | 뜻 | 재개하려면 |
|---|---|---|
| `paid_unfulfilled_count` | 결제완료 후 10분 넘게 미지급인 건수 | 0 |
| `money_review_count` | 돈이 걸린 수동 확인 주문 수 | 0 |
| `cancel_unprocessed_active_count` | 취소 미처리인데 크레딧을 쓸 수 있는 건수 | 0 |
| `scheduler_unhealthy` | 대사 작업이 건강하지 않음 | false |
| `consecutive_failures`, `last_succeeded_at` | 참고용(대사 작업의 연속 실패 횟수, 마지막 성공 시각) | — |

건수는 **10분이 넘은 건만** 셉니다. 문제가 생긴 직후에는 0으로 보일 수 있으니, 방금 생긴 건이 있으면 그 건을 처리한 뒤 재개하고 10분 뒤 다시 확인합니다([1-4](#1-4-판매가-자동으로-꺼졌을-때의-순서)의 6번).

2. **미해소 경보**를 봅니다([1-1](#1-1-경보를-어디서-보나)의 조회). 경보가 남아 있어도 재개 자체는 막히지 않지만, 원인을 확인하고 관리자 화면에서 해소한 뒤 재개합니다.
3. [2-0](#2-0-지금-상태-보기)으로 어느 스위치가 꺼져 있는지 봅니다.

### 2-4. 재개하기 (SQL)

재개는 **Supabase SQL Editor에서만** 할 수 있습니다(관리자 화면이나 서버에는 재개 권한을 주지 않았습니다). [2-0](#2-0-지금-상태-보기)에서 `false`인 쪽을 켭니다.

자동 점검이 껐다면(보통 페이앱 스위치):

```sql
SELECT public.resume_payment_sales('payapp', '처리자 이름', '재개 사유(원인과 조치)');
```

버튼으로 껐다면(전체 스위치):

```sql
SELECT public.resume_payment_sales('master', '처리자 이름', '재개 사유(원인과 조치)');
```

실행 뒤 [2-0](#2-0-지금-상태-보기)을 다시 실행해 두 스위치가 모두 `true`인지 확인하고, 대시보드에 초록 "충전 판매 중"이 보이는지 봅니다. 올려 둔 중지 공지([2-8](#2-8-판매-중지-동안-고객-안내))도 내립니다.

### 2-5. 둘 다 꺼진 경우

버튼으로 끈 뒤 자동 점검도 껐거나 그 반대면 두 스위치가 모두 `false`입니다. 이때는 **위 두 문장을 모두** 실행해야 판매가 재개됩니다(순서는 상관없습니다). 하나만 켜면 여전히 충전할 수 없습니다.

### 2-6. 오류 코드의 뜻

| 오류 | 뜻 | 할 일 |
|---|---|---|
| `PAYMENT_SALES_RESUME_BLOCKED` | 막는 조건이 남아 재개를 거부했습니다. 오류의 DETAIL에 남은 건수가 나옵니다. | [2-3](#2-3-재개-전-확인)의 표에서 0이 아닌 항목을 [1-2](#1-2-경보-코드별-대응표)대로 처리하고 다시 시도합니다. |
| `PAYMENT_SALES_ALREADY_ON` | 그 스위치는 이미 켜져 있습니다. | [2-0](#2-0-지금-상태-보기)으로 꺼진 쪽이 어느 것인지 확인합니다. |
| `PAYMENT_SALES_CONFIG_INCOMPLETE` | 페이앱 가맹점 ID가 비어 있어 켤 수 없습니다. | 개발 담당자에게 알립니다. |
| `PAYMENT_SALES_SCOPE_INVALID` | 첫 번째 값이 `'master'`나 `'payapp'`이 아닙니다. | 오타를 고칩니다. |
| `PAYMENT_SALES_REASON_REQUIRED` | 처리자 이름이나 사유가 비어 있습니다. | 둘 다 적습니다. |
| `PAYMENT_RUNTIME_CONFIG_MISSING` | 스위치 설정 행이 없습니다. | 개발 담당자에게 알립니다. |

### 2-7. 휴대폰만 있을 때

1. 휴대폰 브라우저로 사이트의 관리자 로그인 화면(`/admin/login`)에 들어가 관리자 계정으로 로그인합니다.
2. 대시보드(`/admin`) 맨 위의 **"충전 판매 중지"** 버튼으로 중지합니다([2-1](#2-1-버튼으로-중지하기-가장-빠름)과 같습니다).
3. **재개는 휴대폰에서 버튼으로 할 수 없습니다.** Supabase SQL Editor가 필요하므로 PC를 쓸 수 있을 때 합니다(휴대폰 브라우저에서 Supabase 대시보드를 쓸 수 있는지는 **확인 필요**).

### 2-8. 판매 중지 동안 고객 안내

코드로 확인한, 지금 실제로 쓸 수 있는 공지 수단입니다.

| 수단 | 방법 | 한계 |
|---|---|---|
| 충전 화면의 자동 문구 | 아무것도 하지 않아도 "결제 기능을 준비 중입니다"가 나옵니다. | 문구를 바꿀 수 없고, 언제 재개되는지 알려 주지 못합니다. |
| 홈 광고 배너 | `/admin/main-ad-settings`("(임시)메인광고설정") → "광고 추가" → 공지 이미지를 올리고 "광고 노출"을 켠 뒤 "저장". 재개하면 그 광고를 끄거나 삭제하고 저장합니다. | **이미지가 필요합니다**(PC 이미지 필수, 권장 1920×720). 글자만으로는 올릴 수 없으므로 공지용 이미지를 미리 만들어 둡니다. **국어·영어 설정이 따로**이므로 두 과목 모두에 올립니다. |
| 문의 답변 | 문의가 온 고객에게 [12-1](#12-1-충전-판매-일시-중지) 문구로 답합니다. | 문의한 고객에게만 전달됩니다. |

사이트 전체에 글자 공지를 띄우는 기능(공지 띠, 공지 게시판)은 없습니다.

### 2-9. 요금제 하나만 내리기

전체 판매는 두고 특정 요금제만 숨기고 싶을 때입니다.

1. `/admin/pricing`("요금제 관리")에서 해당 요금제의 "상태" 칸 스위치를 누릅니다.
2. 확인 창 **"요금제 판매 중지"**에서 내용을 읽고 **"판매 중지"**를 누릅니다.
3. "'○○' 요금제를 비활성으로 바꿨습니다."가 나오면 끝입니다. 고객의 충전 화면에서 그 요금제가 바로 사라집니다. 이미 결제한 건에는 영향이 없습니다.
4. "판매 상태를 바꾸지 못했습니다…"가 나오면 목록에 보이는 현재 상태를 확인하고 다시 시도합니다.

다시 켤 때는 같은 스위치를 눌러 **"판매 시작"**을 누릅니다. 켜는 즉시 누구나 결제할 수 있습니다.

## 3. RB-4 잘못 지급한 크레딧 회수

- **언제**: 크레딧 지급 창에서 다른 회원에게 지급했거나, 금액을 잘못 넣었을 때.
- **누가**: 대표.
- **지금 상태**: **회수하는 화면이 없습니다.** 지급 창에도 "지급 후에는 취소할 수 없으며 사용자에게 알림이 발송됩니다."라고 나옵니다. 회수하려면 [0-3](#0-3-sql-규칙--반드시-지킬-것) 규칙대로 SQL을 새로 작성하고 검증해야 하며 **1~2일**이 걸립니다. 원천(`credit_sources`), 거래 내역(`credit_transactions`), 회원 잔액(`profiles.credits`)을 한 번에 맞게 고쳐야 해서 즉석으로 고치면 잔액이 어긋납니다. **직접 UPDATE하지 않습니다.**

### 그동안 할 일

1. **무엇이 잘못 나갔는지 기록합니다.** 해당 회원의 최근 지급을 조회합니다(이메일만 바꿔 실행).

```sql
SELECT cs.id                 AS 원천_id,
       cs.source_category    AS 분류,
       cs.initial_credits    AS 지급량,
       cs.remaining_credits  AS 남은량,
       cs.status             AS 상태,
       cs.created_at AT TIME ZONE 'Asia/Seoul' AS 지급_한국시간
  FROM public.credit_sources cs
  JOIN public.profiles p ON p.id = cs.user_id
 WHERE p.email = '회원이메일@example.com'
   AND cs.source_category IN ('admin_grant', 'bonus', 'system_refund')
 ORDER BY cs.created_at DESC
 LIMIT 20;
```

`분류`는 지급 창의 사유 카테고리에 따라 정해집니다. "보상 (장애/오류)"·"기타"는 `admin_grant`, "이벤트 당첨"은 `bonus`, "환불 (취소/철회)"는 `system_refund`입니다. `지급량`과 `남은량`의 차이가 이미 쓴 크레딧입니다.

2. **해당 회원에게 바로 안내합니다.** [12-6](#12-6-잘못-지급한-크레딧-회수-안내) 문구를 씁니다. 회원은 이미 "크레딧이 지급되었습니다" 알림을 받았을 수 있습니다.
3. **받아야 했던 회원에게는 정상 지급을 따로 합니다**(크레딧 지급 창, [6절](#6-rb-7-하자-상품-환불) 참고).
4. **회수 SQL 작업을 시작합니다**: 개발 담당자에게 위 조회 결과(원천 id, 지급량, 남은량)를 전달 → 덤프 → 작성 → `BEGIN … ROLLBACK` 리허설 → 전문 검증 3명 → 대표 승인 → 적용.

### 대표가 정해야 하는 것

**회수 전에 회원이 이미 써 버린 크레딧을 어떻게 할지는 대표 결정 사항입니다.** 정해진 기준이 아직 없습니다. 선택지는 대략 ① 남은 만큼만 회수하고 쓴 것은 포기, ② 쓴 만큼을 회원에게 따로 청구, ③ 쓴 것으로 산 자료의 이용을 막음 — 인데, ②·③은 회원과의 분쟁 소지가 있으니 금액이 클 때만 검토합니다. 결정한 내용은 회수 SQL의 검증 자료에 함께 적습니다.

### 예방

- 지급 창은 한 번에 **최대 10,000 크레딧**까지만 지급합니다.
- 마지막 단계 "지급 내용을 확인해주세요"에서 **받는 사람 이메일과 금액**을 소리 내어 한 번 읽고 "지급 확정"을 누릅니다.
- "이 창에서 보낸 이전 지급이 이미 처리되었습니다…"라는 오류가 나오면 **다시 누르지 말고** 크레딧 관리 화면의 내역에서 지급이 됐는지 먼저 확인합니다.

## 4. RB-5 영수증(매출전표) 요청

- **언제**: 고객이 결제 영수증·매출전표를 요청할 때.
- **누가**: 대표(페이앱 판매자 관리자 화면은 대표만 씁니다).
- **지금 상태**: 사이트에는 영수증을 발급하는 화면이 없습니다. 페이앱 판매자 관리자 화면에서 발급합니다.

### 순서

1. 고객의 결제 건과 **페이앱 결제요청번호**를 찾습니다(이메일만 바꿔 실행).

```sql
SELECT po.order_id                    AS 주문번호,
       ppt.provider_transaction_id    AS 페이앱_결제요청번호,
       po.plan_name_snapshot          AS 요금제,
       po.expected_amount             AS 결제금액,
       pm.label                       AS 결제수단,
       po.status                      AS 주문상태,
       po.approved_at AT TIME ZONE 'Asia/Seoul' AS 결제_한국시간
  FROM public.payment_orders po
  JOIN public.payment_provider_transactions ppt ON ppt.payment_order_id = po.id
  LEFT JOIN public.payment_methods pm
         ON pm.code = po.payment_method_code AND pm.provider = po.provider
  JOIN public.profiles p ON p.id = po.user_id
 WHERE p.email = '회원이메일@example.com'
   AND po.provider = 'payapp'
   AND po.status IN ('completed', 'refunded')
 ORDER BY po.approved_at DESC;
```

2. 고객이 말한 결제일·금액과 맞는 줄의 **페이앱_결제요청번호**를 적어 둡니다.
3. 페이앱 판매자 관리자 화면에 로그인해 그 번호로 결제를 찾고 영수증(매출전표)을 발급하거나 고객에게 보냅니다. **페이앱 관리자 화면의 정확한 메뉴 이름과 발급 방식(메일 발송인지, 주소 전달인지)은 코드로 확인할 수 없어 "확인 필요"입니다.** 출시 전에 한 번 직접 해 보고 이 자리에 메뉴 이름을 적어 두는 것을 권합니다.
4. 문의에 답변합니다([12-7](#12-7-영수증-안내)).

`주문상태`가 `refunded`인 건은 이미 환불된 결제입니다. 세금계산서·현금영수증처럼 다른 증빙을 요청받았을 때의 처리는 이 문서 범위 밖이며 **확인 필요**입니다.

## 5. RB-6 충전 환불 — 휴대폰 결제 당월 경과·정산 후 환불 포함

- **언제**: 고객이 충전한 크레딧의 환불을 요청했을 때.
- **누가**: 대표.
- **어디서**: `/admin/refunds`("환불 관리")의 충전 환불 요청 표.

### 5-1. 고객이 환불을 신청할 수 있는 조건(사이트가 자동으로 검사)

고객은 마이페이지의 크레딧 화면(`/mypage/credits`)에서 구매 건별로 환불을 신청합니다. 다음 경우에는 신청 자체가 거부됩니다(코드 확인).

- 결제로 충전한 크레딧이 아닌 경우(관리자 지급 등)
- 그 구매 건의 크레딧을 **조금이라도 사용한 경우**
- **구매 후 7일이 지난 경우**
- 사용기한이 만료된 경우
- 이미 환불 처리 중이거나 완료된 경우

신청이 접수되면 그 크레딧은 묶여서(동결) 쓸 수 없게 됩니다. 조건에 맞지 않지만 사정상 환불해 줘야 하는 경우의 처리 방법은 화면에 없으며, [0-3](#0-3-sql-규칙--반드시-지킬-것) 규칙의 대상입니다.

### 5-2. 상태의 뜻과 할 일

| 화면 표시 | DB 값 | 뜻 | 할 일 |
|---|---|---|---|
| 대기중 | `pending_review` | 고객이 신청했고 아직 처리 전 | "승인" 또는 "거부" |
| 처리중 | `processing` | 결제사에 취소를 보내고 결과를 기다리는 중 | 잠시 기다립니다. 10분이 넘으면 대사 작업이 자동으로 "재처리 필요"로 바꾸고 `PAYAPP_REFUND_PROCESSING_STUCK` 경보를 남깁니다. 15분이 지나도 "처리중"이면 개발 담당자에게 알립니다. |
| 환불 완료 | `completed` | 환불과 크레딧 회수가 끝남 | 없음 |
| 거부 | `rejected` | 거부했고 크레딧 동결이 풀림 | 없음 |
| 재처리 필요 | `retryable_failed` | 취소 시도가 일시적으로 실패 | **먼저 페이앱 관리자 화면에서 그 결제가 이미 취소됐는지 확인합니다.** 취소되지 않았으면 "결제 처리" 칸의 오류 코드를 보고 "승인"을 다시 누릅니다. 이미 취소돼 있으면 다시 승인하지 말고 개발 담당자에게 알립니다(돈은 이미 돌아갔으므로 계좌 송금을 하면 안 됩니다). 계속 실패해도 개발 담당자에게 알립니다. |
| 수동 확인 필요 | `manual_review` | 자동으로 취소할 수 없어 사람이 처리해야 함 | [5-3](#5-3-수동-완료--자동-취소가-안-되는-경우) |

화면 위쪽의 필터 기본값은 "처리할 건 (대기·재처리·수동 확인)"입니다.

**승인**: "승인" → 창에서 내용 확인 → **"원 결제수단 환불"**. 페이앱에 전액 취소를 먼저 보내고, 취소가 확인되면 크레딧을 회수합니다. 끝나면 "원 결제수단 환불과 크레딧 회수가 완료되었습니다."가 나오고 고객에게 사이트 알림이 남습니다.

**거부**: "거부" → 필요하면 "관리자 메모 (선택)" → **"거부"**. 환불 요청이 닫히고 크레딧을 다시 쓸 수 있게 됩니다. 수동 확인 필요 상태의 건을 거부할 때는 "결제사 관리자에서 이 결제가 취소되지 않았음을 확인했습니다." 확인란과 처리 메모가 모두 필요합니다. **거부할 때는 고객에게 알림이 가지 않으므로** 사유를 따로 안내합니다([12-5](#12-5-환불-거절)).

### 5-3. 수동 완료 — 자동 취소가 안 되는 경우

"승인"을 눌렀는데 페이앱이 취소를 거절하면(**휴대폰 결제에서 결제한 달이 지난 경우, 이미 정산이 끝난 경우** 등) 요청이 "수동 확인 필요"로 바뀝니다. 관리자가 직접 결제를 확인해 준 주문도 자동 취소하지 않고 수동 확인으로 보냅니다. 이때는 **돈을 먼저 돌려준 뒤** 화면에 "완료"를 기록합니다.

1. **돈을 돌려줍니다.** 방법은 둘 중 하나입니다.
   - **페이앱 관리자 화면에서 취소 요청(정산금 반환)**: 가능한 경우 이쪽이 깔끔합니다. 페이앱 화면의 정확한 메뉴 이름은 **확인 필요**입니다.
   - **고객 계좌로 송금**: 휴대폰 결제 당월 경과처럼 결제사 취소가 안 될 때 씁니다. 아래 5-4를 봅니다.
2. `/admin/refunds`의 해당 줄에서 **"수동 완료"**를 누릅니다.
3. 창에서 다음을 입력합니다.
   - **외부 처리 방식**: "페이앱 취소 요청(정산금 반환)" / "고객 계좌 송금" / "결제사 관리자에서 취소" 중 실제로 한 것
   - **고객에게 실제로 환불한 총액 (원)**: 실제 돌려준 금액
   - (부분취소 건만) **회수할 크레딧**: 직접 입력. 그 밖의 건은 남은 크레딧을 모두 회수합니다.
   - **처리 메모 (필수)**: 언제, 어떤 방법으로, 얼마를 돌려줬는지
4. **"완료 처리"**를 누릅니다. "수동 환불 완료와 크레딧 회수를 기록했습니다."가 나오면 끝입니다. 고객에게 사이트 알림이 남습니다(계좌 송금이면 "○○원을 계좌로 환불했습니다.").
5. "미해소 결제 경보"에 이 주문의 경보가 남아 있으면 메모와 함께 직접 해소합니다.

> **이중 환불 주의.** "이미 다른 방식으로 환불이 완료된 요청입니다. 계좌로 송금했다면 이중 환불이므로 회수해야 합니다."라는 오류가 나오면, 페이앱 취소가 이미 된 건에 계좌 송금까지 한 것입니다. 고객에게 연락해 한쪽을 돌려받아야 합니다. **계좌로 송금하기 전에 반드시 페이앱 관리자 화면에서 그 결제가 취소되지 않았는지 먼저 확인합니다.**

### 5-4. 계좌 송금으로 환불할 때(휴대폰 결제 당월 경과·정산 후)

1. 고객에게 1:1 문의로 환불받을 **은행·계좌번호·예금주**를 받습니다([12-3](#12-3-환불-접수) 문구). 예금주가 결제한 본인인지 확인합니다.
2. 페이앱 관리자 화면에서 그 결제가 **취소되지 않았는지** 확인합니다.
3. 송금합니다. 이체 확인증을 보관합니다.
4. [5-3](#5-3-수동-완료--자동-취소가-안-되는-경우)의 2~5번대로 "수동 완료"를 기록합니다. 외부 처리 방식은 "고객 계좌 송금"입니다.
5. **문의 본문에 남은 계좌번호 처리**: 원래 계획은 송금 뒤 문의 본문의 계좌번호를 지우거나 가리는 것이었습니다. 그런데 **지금 관리자 화면으로는 할 수 없습니다.** 관리자는 문의의 상태와 답변만 고칠 수 있고 고객이 쓴 본문은 고칠 수 없습니다(화면에 기능이 없고, DB 권한도 상태·답변·답변 시각만 허용합니다). 그래서 지금은 이렇게 합니다.
   - **답변란에 계좌번호를 다시 적지 않습니다.**
   - 문의 본문의 계좌번호를 지우려면 [0-3](#0-3-sql-규칙--반드시-지킬-것) 규칙대로 SQL을 작성·검증해 적용합니다(개인정보를 바꾸는 SQL이므로 즉석 실행 금지).
   - 처리할 문의를 기록해 두었다가 한꺼번에 처리합니다.
   - 가능하면 계좌번호는 문의 본문이 아니라 전화나 메일로 받는 방법을 검토합니다. 어느 쪽으로 받을지는 대표가 정합니다.

## 6. RB-7 하자 상품 환불

- **언제**: 고객이 산 자료에 문제(파일이 깨짐, 내용 오류, 다른 자료가 들어 있음 등)가 있다고 할 때.
- **누가**: 대표.
- **두 가지 길**: (가) 고객이 직접 신청한 문제마켓 환불을 승인, (나) 관리자가 크레딧을 보상으로 지급. 자료를 이미 내려받은 고객은 (가)를 신청할 수 없으므로 (나)로 처리합니다.

### (가) 고객이 신청한 문제마켓 환불 승인

고객은 보관함(`/library`)에서 구매 건의 "환불 신청"을 누릅니다. 다음 경우에는 신청이 거부됩니다(코드 확인): **다운로드 이력이 있는 상품**, **구매 후 7일이 지난 상품**, 이미 심사 중이거나 처리된 건, 이 구매를 기준으로 문제(HWP) 차액 업그레이드를 한 경우. 신청하면 심사가 끝날 때까지 그 상품은 내려받을 수 없습니다.

1. `/admin/refunds` 맨 아래 **"문제마켓 환불"** 표에서 "대기중"인 줄을 찾습니다.
2. 상품, 환불 크레딧, 사유를 확인하고 **"승인"** 또는 **"거부"**를 누릅니다.
3. 확인 창에서 필요하면 "처리 메모 (선택)"를 적고 다시 **"승인"**(또는 "거부")을 누릅니다.
   - **승인**: 크레딧을 회원에게 되돌려 주고 그 상품을 더 이상 내려받을 수 없게 합니다. **되돌릴 수 없습니다.**
   - **거부**: 환불 요청이 닫히고 구매는 그대로 유지됩니다. 되돌릴 수 없지만, 환불 가능 기간 안이면 회원이 다시 신청할 수 있습니다.
4. 승인할 때 "요청 ○○C / 복구 가능 ○○C" 안내가 뜨면, 일부 크레딧을 되돌릴 수 없다는 뜻입니다(그 크레딧의 원천이 이미 환불·만료된 경우 등). 확인하면 복구 가능한 만큼만 돌려주고 `MARKET_REFUND_SHORTFALL` 경보가 남습니다. 부족분을 (나)로 보상할지 정합니다.
5. **승인·거부 모두 고객에게 알림이 가지 않습니다**(코드 확인). 문의로 들어온 건이면 답변으로, 아니면 가입 이메일로 결과를 안내합니다([12-4](#12-4-환불-완료), [12-5](#12-5-환불-거절)).

### (나) 크레딧 보상 지급

1. 하자를 확인합니다. 해당 상품을 직접 열어 보고, 상품 자체가 잘못됐으면 `/admin/market/products`("문제마켓 상품 관리")에서 파일을 고치거나 숨김 처리합니다.
2. `/admin/credits`("크레딧 관리") → **"크레딧 지급"** 버튼. (`/admin/users`("사용자 관리")의 회원 줄에 있는 "크레딧 지급" 버튼도 같은 창을 엽니다.)
3. 창 "크레딧 수동 지급"에서 이메일로 회원을 검색해 "선택"합니다.
4. **지급 금액**(한 번에 최대 10,000 크레딧), **사유 카테고리**는 **"환불 (취소/철회)"**, **상세 지급 사유**(필수)를 적고 "다음"을 누릅니다.
   - 사유 카테고리는 4가지입니다: "보상 (장애/오류)", "이벤트 당첨", "환불 (취소/철회)", "기타".
   - **상세 지급 사유는 고객에게 그대로 보입니다.** 알림에 "환불 사유로 ○○ 크레딧이 지급되었습니다. (내용: 적은 사유)"로 나갑니다. 내부 메모처럼 쓰지 말고 고객이 읽어도 되는 문장으로 적습니다(예: "○○ 자료 파일 오류에 대한 환불").
5. "지급 내용을 확인해주세요"에서 받는 사람과 금액을 다시 확인하고 **"지급 확정"**을 누릅니다. **지급 후에는 취소할 수 없습니다**([3절](#3-rb-4-잘못-지급한-크레딧-회수)).
6. `/admin/support`("고객지원 관리")에서 해당 문의에 답변합니다([12-4](#12-4-환불-완료)).

보상으로 크레딧을 지급해도 고객은 그 자료를 계속 내려받을 수 있습니다(구매 기록은 그대로입니다).

## 7. RB-8 문의 답변 안내

- **언제**: 1:1 문의에 답변할 때.
- **누가**: 대표.

### 답변하는 방법

1. `/admin/support`("고객지원 관리") → "문의 목록"에서 문의를 엽니다. 대시보드 "처리 대기"의 "답변 대기 문의"가 이 화면의 "대기 중" 건수입니다.
2. "답변 작성"에 답변을 쓰고 **"답변 등록"**을 누릅니다. "답변이 등록되었습니다."가 나오고 문의 상태가 "해결됨"으로 바뀝니다.

### 답변해도 고객에게 알림이 가나 — 코드 확인 결과

- 답변을 등록하면 사이트 알림 1건이 고객 계정에 저장됩니다(제목 "문의하신 내용에 답변이 등록되었습니다.").
- **하지만 지금 고객이 쓰는 화면(문제마켓 홈·마이페이지 등)의 헤더에는 알림을 보여 주는 곳이 없습니다.** 알림 표시(종 모양)는 옛 헤더에만 있고, 옛 헤더는 충전 결제 화면(`/checkout`) 등 일부에서만 쓰입니다.
- **이메일·문자는 보내지 않습니다.**
- 결론: **고객은 마이페이지의 문의 화면(`/mypage/support`)에 직접 들어가 보기 전에는 답변이 달린 것을 알기 어렵습니다.**

### 그래서 지금은 이렇게 한다

1. 답변을 등록합니다.
2. 급하거나 돈이 걸린 문의(환불, 결제 오류, 계좌 요청)는 **고객의 가입 이메일로 직접 안내 메일을 보냅니다.** 가입 이메일은 문의 상세 창 위쪽에 전화번호와 함께 표시됩니다.
3. 보내는 메일 계정은 사이트 공식 문의 메일로 통일합니다. 어느 계정으로 보낼지는 대표가 정해 이 자리에 적어 둡니다(**확인 필요** — 코드에 정해진 발신 계정이 없습니다).
4. 메일에는 답변 전문을 옮기지 말고 "답변이 등록되었다"는 사실과 확인 경로만 적습니다([12-8](#12-8-문의-답변-도착-안내-메일)). 개인정보(계좌번호 등)를 메일에 적지 않습니다.

### 그 밖에 알아 둘 것

- 고객이 삭제한 문의는 필터에서 "삭제 포함"을 켜거나 상태 "고객삭제"를 고르면 보입니다.
- 문의가 새로 들어와도 관리자에게 자동으로 알려 주는 것은 확실하지 않습니다. 코드에는 문의 등록 때 슬랙으로 보내는 부분이 남아 있지만, 서버에 슬랙 주소가 설정되어 있는지는 **확인 필요**입니다(환경 설정 파일은 열어 보지 않았습니다). 대시보드의 "답변 대기 문의" 숫자를 직접 확인하는 것을 기본으로 합니다.

## 8. RB-9 CS 담당자 퇴사

- **언제**: 관리자 계정을 쓰던 사람이 그만둘 때.
- **누가**: 대표.
- **원칙**: 관리자 계정은 **삭제하지 말고 접근만 막습니다.**

### 왜 삭제하지 않나

`/admin/admin-accounts`("관리자 ID 관리")에 "삭제" 버튼이 있지만, 그 계정에 고객지원 문의·결제 시도·결제 주문 이력이 하나라도 있으면 삭제가 거부됩니다("○○ 이력이 있는 계정은 삭제할 수 없습니다. 기록 보존이 필요하면 비밀번호 변경으로 접근만 차단해주세요."). 또 삭제에 성공하면 그 사람이 처리한 환불·지급 기록에서 "누가 처리했는지"를 알 수 없게 됩니다.

### 지금 할 수 있는 방법

| 방법 | 어떻게 | 비고 |
|---|---|---|
| **비밀번호 재설정으로 접근 차단** (지금 화면으로 가능) | `/admin/admin-accounts`에서 그 계정 줄의 "새 비밀번호" 칸에 아무도 모르는 새 비밀번호(8자 이상)를 넣고 **"비밀번호 재설정"**. | 그 사람이 새로 로그인할 수 없게 됩니다. 다만 코드에는 이미 로그인해 둔 브라우저를 끊는 처리가 없습니다. 실제로 바로 끊기는지는 **확인 필요**이며, 확인되기 전까지는 **기존 로그인은 끊기지 않는다고 보고 접근이 완전히 막힌 것으로 여기지 않습니다.** 퇴사 당일 바로 처리하고, 그 사람이 쓰던 기기에서 로그아웃했는지도 직접 확인합니다. |
| **관리자 권한 해제**(`is_admin` 값을 끔) | 지금은 **화면이 없습니다.** SQL이 필요하며 권한을 바꾸는 작업이므로 [0-3](#0-3-sql-규칙--반드시-지킬-것) 규칙대로 작성·검증해 적용합니다. | 권한 해제 화면은 이후 개발 계획에 있습니다. |

자기 자신의 계정과 마지막 남은 관리자 계정은 삭제할 수 없게 되어 있습니다.

### 외부 서비스 계정 회수 체크리스트

퇴사 당일 확인합니다. 해당 없는 항목은 "해당 없음"으로 표시합니다.

- [ ] 사이트 관리자 계정: 비밀번호 재설정 완료
- [ ] 페이앱 판매자 관리자: 원래 대표만 쓰는 계정입니다. 알려 준 적이 있으면 비밀번호 변경
- [ ] Supabase: 프로젝트 구성원에서 제거
- [ ] Vercel: 프로젝트(팀) 구성원에서 제거
- [ ] 슬랙: 채널·워크스페이스에서 제거
- [ ] 고객 응대용 메일 계정: 비밀번호 변경, 자동 전달 설정 확인
- [ ] 공용으로 쓰던 그 밖의 계정(카페 운영 계정, 문서 공유 등): 비밀번호 변경
- [ ] 개인 기기에 내려받은 고객 정보(엑셀, 캡처 등) 삭제 확인

## 9. RB-10 월말 정산 대조

- **언제**: 매달 초, 지난달 매출을 페이앱 정산 자료와 맞춰 볼 때.
- **누가**: 대표.
- **기준**: 금액의 기준은 **페이앱 정산 자료**입니다. 아래 조회는 우리 DB가 그 자료와 맞는지 보는 용도입니다. 모든 조회는 **한국 시간 기준 월 경계**로 셉니다.

### 9-1. 월별 결제 합계 (결제수단별)

```sql
SELECT to_char(po.approved_at AT TIME ZONE 'Asia/Seoul', 'YYYY-MM') AS 결제월,
       COALESCE(pm.label, po.payment_method_code)                   AS 결제수단,
       COUNT(*)                                                     AS 결제건수,
       SUM(po.expected_amount)                                      AS 결제금액
  FROM public.payment_orders po
  LEFT JOIN public.payment_methods pm
         ON pm.code = po.payment_method_code AND pm.provider = po.provider
 WHERE po.provider = 'payapp'
   AND po.provider_environment = 'live'
   AND po.status IN ('completed', 'refunded')
   AND po.approved_at IS NOT NULL
 GROUP BY 1, 2
 ORDER BY 1 DESC, 2;
```

- `completed`는 결제되어 크레딧이 지급된 주문, `refunded`는 결제됐다가 나중에 환불된 주문입니다. **결제된 달의 매출에는 둘 다 넣고**, 환불은 아래 9-2에서 환불된 달 기준으로 따로 셉니다.
- 수동 확인 중(`manual_review`)인 주문은 여기에 들어가지 않습니다. 월말에 수동 확인 주문이 남아 있으면 먼저 처리합니다.

### 9-2. 월별 환불 합계

```sql
SELECT to_char(COALESCE(rr.provider_cancelled_at, rr.processed_at) AT TIME ZONE 'Asia/Seoul', 'YYYY-MM') AS 환불월,
       rr.origin                AS 환불_경위,
       COUNT(*)                 AS 환불건수,
       SUM(rr.refund_amount)    AS 환불금액
  FROM public.refund_requests rr
 WHERE rr.provider = 'payapp'
   AND rr.status = 'completed'
 GROUP BY 1, 2
 ORDER BY 1 DESC, 2;
```

- `환불_경위`: `user`는 고객이 신청한 환불, `external_cancel`은 페이앱 쪽에서 먼저 취소된 건, `partial_cancel`은 부분취소 건입니다.
- 환불 시각은 결제사 취소 시각(`provider_cancelled_at`)을 쓰고, 계좌 송금처럼 그 값이 없으면 관리자 처리 시각(`processed_at`)을 씁니다.
- 계좌 송금으로 환불한 건은 페이앱 정산 자료에 취소로 나오지 않습니다. 아래 9-3으로 따로 뽑아 이체 내역과 맞춥니다.

### 9-3. 수동 완료한 환불 목록(처리 방식별)

```sql
SELECT a.created_at AT TIME ZONE 'Asia/Seoul' AS 처리_한국시간,
       a.external_method                      AS 처리방식,
       po.order_id                            AS 주문번호,
       rr.refund_amount                       AS 환불금액,
       a.recovered_credits                    AS 회수한_크레딧,
       a.note                                 AS 메모
  FROM public.payment_admin_actions a
  LEFT JOIN public.refund_requests rr ON rr.id = a.refund_request_id
  LEFT JOIN public.payment_orders po ON po.id = COALESCE(a.payment_order_id, rr.payment_order_id)
 WHERE a.external_method IS NOT NULL
 ORDER BY a.created_at DESC;
```

`처리방식`은 `bank_transfer`(고객 계좌 송금), `payapp_cancel_request`(페이앱 취소 요청), `provider_admin_cancel`(결제사 관리자에서 취소)입니다. 이 목록에는 환불 요청의 "수동 완료"뿐 아니라 수동 확인 주문에서 "취소 처리 확인"으로 기록한 건도 함께 나옵니다. 그런 줄은 연결된 환불 요청이 없어 `환불금액`이 비어 있습니다.

### 9-4. 대조 순서

1. 페이앱 판매자 관리자 화면에서 지난달 결제·취소 내역을 내려받습니다(메뉴 이름 **확인 필요**).
2. 페이앱 내역에서 **사이트 밖(카페) 판매분을 빼고** 사이트 결제만 남깁니다. 사이트 결제는 우리 DB의 결제요청번호와 맞춰 가릅니다.
3. 9-1의 건수·금액과 맞는지 봅니다. 9-2의 환불 건수·금액도 맞춥니다.
4. 맞지 않으면 건별 목록으로 어긋난 건을 찾습니다(월만 바꿔 실행. 아래는 2026년 11월).

```sql
SELECT po.order_id                    AS 주문번호,
       ppt.provider_transaction_id    AS 페이앱_결제요청번호,
       po.expected_amount             AS 금액,
       po.status                      AS 주문상태,
       po.approved_at AT TIME ZONE 'Asia/Seoul' AS 결제_한국시간
  FROM public.payment_orders po
  LEFT JOIN public.payment_provider_transactions ppt ON ppt.payment_order_id = po.id
 WHERE po.provider = 'payapp'
   AND po.provider_environment = 'live'
   AND po.status IN ('completed', 'refunded')
   AND po.approved_at >= ('2026-11-01'::timestamp AT TIME ZONE 'Asia/Seoul')
   AND po.approved_at <  ('2026-12-01'::timestamp AT TIME ZONE 'Asia/Seoul')
 ORDER BY po.approved_at;
```

5. 페이앱에는 있는데 우리 DB에 없는 사이트 결제, 또는 그 반대가 있으면 **고치지 말고** 개발 담당자에게 알립니다.

> 참고: 부분취소 건의 `refund_amount`는 수동 완료 전에는 신청 기준액(전액)으로 들어 있습니다. 완료(`completed`)된 건만 세므로 위 합계에는 영향이 없지만, 부분취소가 있었던 달은 페이앱 자료를 기준으로 금액을 다시 확인합니다. 세금 신고용 수치는 이 조회가 아니라 페이앱 정산 자료를 씁니다.

## 10. RB-11 개인정보 열람·삭제·탈퇴 요청

- **언제**: 고객이 자기 정보를 보여 달라거나, 지워 달라거나, 탈퇴하겠다고 할 때.
- **누가**: 대표.

### 10-1. 지금 탈퇴 기능이 하는 일 (코드 확인)

고객은 마이페이지의 회원 탈퇴 화면(`/mypage/withdraw`)에서 이메일을 다시 입력해 스스로 탈퇴합니다.

| 경우 | 결과 |
|---|---|
| **결제 이력이 없는 회원**(충전 주문이나 결제 시도가 한 번도 없음) | 즉시 탈퇴됩니다. 그 회원의 문제·문제지, 1:1 문의, 크레딧 거래 내역, 회원 정보(프로필)를 지우고 로그인 계정까지 삭제합니다. 되돌릴 수 없습니다. |
| **결제 이력이 있는 회원**(결제 주문이나 결제 시도가 1건이라도 있음 — 결제를 끝내지 않고 창만 열었던 경우도 포함) | **탈퇴가 거부됩니다.** 화면에 "결제 이력이 있는 계정은 관련 법령에 따른 기록 보존을 위해 즉시 삭제할 수 없습니다. 고객지원(1:1 문의)으로 탈퇴를 요청해주세요."가 나옵니다. |

> 주의: 탈퇴 화면의 안내문은 "결제 및 크레딧 내역"도 삭제된다고 적혀 있지만, 실제로는 결제 이력이 있으면 탈퇴 자체가 되지 않습니다. 안내문과 실제 동작이 다르다는 점을 알고 응대합니다.

위 표에 적지 않은 나머지 데이터도 회원 정보(프로필)가 지워질 때 DB 연결 규칙에 따라 함께 지워집니다(2026-11-13 DB 확인). 크레딧 원천과 사용 기록(`credit_sources`, `credit_consumption`), 문제마켓 구매·이용 권한·다운로드 기록(`market_purchases`, `market_purchase_orders`, `market_entitlements`, `market_download_events`), 후기(`market_item_reviews`), 환불 요청(`market_refund_requests`, `refund_requests`), 알림(`notifications`), 장바구니(`market_cart_items`)입니다. 즉 결제 이력이 없는 회원이 탈퇴하면 관리자 지급 크레딧으로 산 자료의 구매 기록과 후기도 남지 않습니다.

### 10-2. 결제 이력이 있는 회원의 탈퇴 요청

**지금은 처리하는 화면이 없습니다.** 결제 기록은 법령상 일정 기간 보관해야 하므로 회원 정보를 통째로 지울 수 없고, 이름·연락처 같은 개인정보만 알아볼 수 없게 바꾸는(익명화) 작업이 필요합니다. 이 작업은 [0-3](#0-3-sql-규칙--반드시-지킬-것) 규칙대로 **필요할 때 SQL을 작성 → 리허설 → 전문 검증 3명 → 대표 승인 → 적용**합니다(1~2일).

1. 문의로 탈퇴 요청을 받으면 본인 확인을 합니다(가입 이메일로 로그인해 남긴 1:1 문의면 본인으로 봅니다).
2. 결제 이력을 확인합니다(이메일만 바꿔 실행).

```sql
SELECT p.id                                   AS 회원_id,
       p.email,
       p.created_at AT TIME ZONE 'Asia/Seoul' AS 가입_한국시간,
       p.credits                              AS 남은_크레딧,
       (SELECT COUNT(*) FROM public.payment_orders po WHERE po.user_id = p.id)   AS 결제주문_수,
       (SELECT COUNT(*) FROM public.checkout_attempts ca WHERE ca.user_id = p.id) AS 결제시도_수,
       (SELECT COUNT(*) FROM public.support_tickets st WHERE st.user_id = p.id)   AS 문의_수
  FROM public.profiles p
 WHERE p.email = '회원이메일@example.com';
```

3. **남은 크레딧과 진행 중인 환불이 있는지** 봅니다. 남은 크레딧이 있으면 탈퇴 시 소멸됨을 알리고 동의를 받거나, 환불 조건에 맞으면 환불을 먼저 처리합니다.
4. 고객에게 접수 안내를 합니다([12-9](#12-9-탈퇴개인정보-삭제-요청-접수)). 그때부터 그 계정으로 더 결제하지 않도록 안내합니다.
5. 개발 담당자와 익명화 SQL 작업을 시작합니다. 어떤 항목을 지우고 어떤 기록을 얼마 동안 남길지는 법령 기준을 확인해 대표가 정합니다(**확인 필요** — 보관 기간과 대상은 이 문서에서 정하지 않았습니다).
6. 적용 뒤 고객에게 완료를 알립니다.

### 10-3. 개인정보 열람 요청

1. 본인 확인을 합니다.
2. Supabase SQL Editor에서 그 회원의 정보를 조회합니다(이메일만 바꿔 실행).

```sql
SELECT email, phone, birthdate, organization, gender, address,
       provider    AS 가입_방식,
       role        AS 회원_유형,

  FROM public.profiles
```

필요하면 결제 내역([4절](#4-rb-5-영수증매출전표-요청)의 조회)과 문의 내역도 함께 조회합니다.

3. 결과를 정리해 **가입 이메일로** 회신합니다. 다른 주소로 보내 달라는 요청은 본인 확인이 더 필요합니다. 조회 결과를 내려받은 파일은 회신 뒤 지웁니다.

### 10-4. 개인정보 일부 삭제·정정 요청

## 11. 그 밖의 절차

### 11-1. 비밀번호 분실 문의

**코드 확인 결과, 지금 사이트에는 비밀번호를 잊은 고객이 스스로 재설정하는 기능이 없습니다.**

- 로그인 화면(`/login`)에 "비밀번호 찾기"가 없습니다.
- 마이페이지의 비밀번호 변경은 **기존 비밀번호를 알아야** 쓸 수 있습니다.
- 재설정 메일을 받은 고객이 새 비밀번호를 입력할 화면도 없습니다. 그래서 Supabase 대시보드에서 복구 메일을 보내도 지금은 고객이 새 비밀번호를 정할 수 없습니다(메일 발송 설정이 끝났는지, 수신이 되는지도 **확인 필요**).

지금 할 수 있는 대응입니다.

| 고객 유형 | 대응 |
|---|---|
| 카카오로 가입한 고객 | 비밀번호가 없습니다. 로그인 화면의 "카카오로 시작하기"로 로그인하시도록 안내합니다. |
| 이메일로 가입했고 결제·구매 이력이 없는 고객 | 다른 이메일로 새로 가입하시도록 안내할 수 있습니다. |
| 이메일로 가입했고 크레딧·구매 자료가 있는 고객 | 사이트 기능으로는 복구할 수 없습니다. 본인 확인(가입 이메일로 보낸 메일에 답장을 받는 등) 뒤 개발 담당자와 처리 방법을 정합니다. 계정 정보를 바꾸는 작업이므로 [0-3](#0-3-sql-규칙--반드시-지킬-것) 규칙을 따릅니다. |

비밀번호 재설정 기능은 개발 계획에 있습니다. 그 전까지는 [12-10](#12-10-비밀번호-분실) 문구로 안내합니다.

관리자 계정의 비밀번호는 다른 관리자가 `/admin/admin-accounts`의 "비밀번호 재설정"으로 바꿔 줄 수 있습니다.

### 11-2. 꺼 둔 기능 다시 켜기

쓰지 않는 기능은 묶음 단위로 꺼 두었습니다. 꺼진 묶음의 메뉴는 보이지 않고, 주소를 직접 쳐도 열리지 않습니다(대표 계정도 같습니다).

지금 꺼져 있는 묶음을 보는 조회입니다.

```sql
SELECT key, value, updated_at AT TIME ZONE 'Asia/Seoul' AS 변경_한국시간
  FROM public.system_settings
 WHERE key IN ('admin_disabled_features', 'site_disabled_features');
```

| 설정 이름 | 대상 | 지금 꺼져 있는 묶음 (2026-11-13 확인) |
|---|---|---|
| `admin_disabled_features` | 관리자 화면 | `question_bank`(문제은행), `ai_generation`(AI 문제 유형·AI 연결·AI 생성 로그), `generate`(문제생성 상품), `passages`(지문), `source_configs`(출처 관리), `labels`(표기값 관리), `signup_roles`(회원가입 관리), `landing_pages`(랜딩페이지 관리) |
| `site_disabled_features` | 고객 화면(옛 기능) | `site_generate`, `site_question_bank`, `site_exam_papers`, `site_passages`, `site_legacy_library`, `site_legacy_mypage`, `site_legacy_landing`, `site_preview` — 닫힌 화면에 들어오면 문제마켓의 해당 화면으로 보내고, 관련 API는 막습니다. |

어느 주소가 어느 묶음인지는 코드(`src/lib/admin-features.ts`, `src/lib/site-features.ts`)에 있고, 어떤 묶음이 꺼져 있는지만 DB에 있습니다.

**다시 켜는 방법**: 설정 값의 `features` 목록에서 해당 묶음 이름을 **뺍니다.** 이 변경은 **운영 DB에서 손으로 값을 고치지 않고**, 마이그레이션 파일(DB 변경 내용을 적어 저장소에 남기는 파일)로 만들어 `BEGIN … ROLLBACK` 리허설을 거친 뒤 적용합니다. 값의 형식이 틀리면 꺼 둔 묶음 전체가 "읽기 실패"로 처리되어 막히기 때문입니다. 적용하면 최대 60초 안에 반영됩니다. 개발 담당자에게 "○○ 묶음을 다시 켜 달라"고 요청하면 됩니다.

**알아 둘 것**: `ai_generation` 묶음이 꺼져 있어 AI 연결 키를 바꾸는 화면도 열리지 않습니다. 그 화면이 필요하면 묶음을 먼저 켜야 합니다.

### 11-3. 매일 새벽 4시 자동 정리

작업 이름은 `market-cleanup-daily`이고, 매일 한국 시간 새벽 4시(UTC 19시)에 국어·영어 각각 한 번씩 실행됩니다.

| 하는 일 | 설명 |
|---|---|
| 임시저장 상품 삭제 | **자동 업로드로 만들어진 임시저장 상품** 가운데 마지막 수정 후 **24시간이 지난 것**을 지웁니다. 구매·다운로드·환불·후기 이력이 있으면 지우지 않습니다. 직접 만든 임시저장 상품이나 공개·숨김 상품은 대상이 아닙니다. |
| 지운 샘플 파일 정리 | 상품에서 뺀 미리보기(샘플) 파일을 저장소에서 지웁니다. |
| 남은 파일 다시 정리 | 상품을 지울 때 저장소에서 지우지 못한 파일을 다시 지웁니다(국어 실행 때 한 번). |

> 주의: 자동 업로드로 올려 두고 **하루 넘게 손대지 않은 임시저장 상품은 다음 새벽에 사라집니다.** 계속 쓸 상품은 24시간 안에 다시 저장하거나 공개·숨김으로 바꿉니다.

**결과 확인**

① 작업이 실행됐는지

```sql
SELECT d.status,
       d.return_message,
       d.start_time AT TIME ZONE 'Asia/Seoul' AS 시작_한국시간
  FROM cron.job_run_details d
  JOIN cron.job j ON j.jobid = d.jobid
 WHERE j.jobname = 'market-cleanup-daily'
 ORDER BY d.start_time DESC
 LIMIT 7;
```

이 작업은 2026-11-13에 등록되어 문서 작성 시점에는 아직 실행 기록이 없습니다. 첫 실행은 2026-11-14 새벽 4시입니다.

② 아직 못 지운 파일이 남았는지

```sql
SELECT source_item_title AS 상품,
       storage_bucket,
       storage_path,
       attempt_count     AS 시도_횟수,
       last_error        AS 마지막_오류,
       created_at AT TIME ZONE 'Asia/Seoul' AS 등록_한국시간
  FROM public.market_storage_cleanup_queue
 ORDER BY created_at;
```

0줄이면 남은 파일이 없습니다. 줄이 남아 있으면 `/admin/market/products`("문제마켓 상품 관리") 위쪽에 "삭제한 상품의 파일 ○개가 아직 저장소에 남아 있습니다…" 안내와 **"남은 파일 다시 정리"** 버튼이 나옵니다. 버튼을 눌러도 남으면 개발 담당자에게 알립니다. 상품 자체는 정상적으로 삭제된 상태이고 파일만 남은 것이라 고객에게는 영향이 없습니다.

③ 서버가 정리 요청에 어떻게 답했는지(**약 6시간분만 남습니다** — 2026-11-13 관찰값. 새벽 4시 결과는 **오전 10시 전에** 확인합니다)

```sql
SELECT id,
       status_code,
       timed_out,
       error_msg,
       left(content, 300) AS 응답_앞부분,
       substring(content from '"storageCleanup":.*$') AS 남은파일_정리,
       created AT TIME ZONE 'Asia/Seoul' AS 받은_한국시간
  FROM net._http_response
 ORDER BY created DESC
 LIMIT 20;
```

이 표에는 5분마다 도는 대사 작업의 응답도 함께 들어 있습니다. 새벽 4시 무렵의 줄 가운데 `응답_앞부분`에 `autoUploadDrafts`가 들어 있는 두 줄(국어·영어)이 정리 작업입니다. 두 줄 모두 `status_code`가 200이고 `응답_앞부분`이 `{"success":true`로 시작하면 정리 요청은 처리된 것입니다. "남은 파일 다시 정리"의 결과는 응답 뒤쪽에 있어 `응답_앞부분`에는 보이지 않으므로 `남은파일_정리` 칸에서 봅니다. 국어 줄은 `"storageCleanup":{…"failed":0,"remaining":0}`처럼 `error`가 없고 `failed`가 0이면 정상입니다. 영어 줄은 이 작업을 하지 않으므로 `"storageCleanup":null`이 정상입니다. `error`가 있거나 `failed`·`remaining`이 0이 아니면 위 ②로 남은 파일을 확인합니다(이 경우에도 `status_code`는 200으로 나옵니다). 오전 10시가 지나 줄이 사라졌으면 위 ①·②로 확인합니다.

### 11-4. 상품 삭제 — "숨김으로 처리됨"의 뜻

`/admin/market/products`에서 상품을 "완전 삭제"하면 결과가 두 가지로 갈립니다.

| 상품 상태 | 결과 | 화면 문구 |
|---|---|---|
| 구매·다운로드·환불·후기 이력이 **하나도 없는** 상품 | DB 데이터와 올린 파일을 모두 지웁니다. 되돌릴 수 없습니다. | (삭제 완료) |
| 이력이 **하나라도 있는** 상품 | **지우지 않고 "숨김"으로 바꿉니다.** | "구매·환불·후기 이력이 있어 삭제하지 않고 숨김 처리했습니다." 여러 개를 한꺼번에 지웠다면 "삭제 ○개 / 이력이 있어 숨김 처리 ○개" |

숨김의 뜻입니다.

- 고객의 문제마켓 목록·검색에서 사라지고 새로 살 수 없습니다.
- **이미 산 고객은 계속 내려받을 수 있습니다.**
- 구매·환불·후기 기록이 그대로 남습니다(기록이 있는 상품은 DB가 삭제를 막도록 되어 있어 지우지 않고 숨깁니다).
- 관리자 목록에는 "숨김" 상태로 남아 있고, 숨김을 해제하면 다시 공개됩니다.

**이것은 오류가 아니라 정해진 동작입니다.** 이력이 있는 상품을 정말로 완전히 없애야 한다면(저작권 문제 등) 구매자 기록까지 건드리는 일이므로 [0-3](#0-3-sql-규칙--반드시-지킬-것) 규칙대로 처리합니다.

### 11-5. 테스트 요금제(`test`) 주의

요금제 목록에 이름이 **`test`**인 요금제(1,000원 / 100 크레딧)가 있고, 2026-11-13 현재 **"판매중"** 상태입니다.

- 판매중인 요금제는 **누구에게나** 충전 화면에 보이고 결제할 수 있습니다. 시험용이라고 해서 대표에게만 보이는 것이 아닙니다.
- 이 요금제로 결제하면 **실제 돈이 결제됩니다**(페이앱은 실결제입니다).
- **출시 전에 대표가 직접 꺼야 합니다**(대표가 직접 끄기로 한 항목입니다). 방법은 [2-9](#2-9-요금제-하나만-내리기)와 같습니다: `/admin/pricing`에서 `test` 줄의 스위치 → "요금제 판매 중지" → "판매 중지".
- 실결제 시험이 필요해 잠깐 켤 때는, 시험이 끝나면 바로 다시 끄고 시험 결제는 환불 처리합니다.

지금 판매중인 요금제를 보는 조회입니다.

```sql
SELECT name, price, credits, is_active, sort_order
  FROM public.pricing_plans
 ORDER BY sort_order;
```
